1.5 Регистрация | Авторизация | JWT token, bcrypt
  JWT token или же токен доступа - это строка разделенная точками на 3 части:
  (JSON WEB TOKEN)
    1 - header (заголовок | алгоритм подписи, тип токена)
    2 - payload (данные о пользователе | email, id, role)
    3 - signature (секретный ключ объявленный на сервере | проверка целостности данных и отправителя)

  Эти данные никак не шифруются, секретной информации они не несут
  Их можно расшифровать на клиенте,
  Но проверить на то валиден токен или нет можно только с помощью секретного ключа
  объявленного на сервере


  План таков:
  Будем проверять почту (существует ли данный пользователь)
  и пароль пользователя (безопасность его входа собственно) с тем что есть в бд,
  Если совпадают, то генерируем JWT token и отправляем его на клиент
  На клиенте сохраняем этот token и прикрепляем к запросам где необходима авторизация


  Реализация:

  Установка - npm i jsonwebtoken bcrypt

  jsonwebtoken - генерация токена
  bcrypt - хэширование паролей, чтобы не хранить в бд, в открытом виде

  Создали секретный ключ в .env для токенов

  Для генерации токена сделали отдельную функцию generateJwt()

  let comparePassword = bcrypt.compareSync(password, user.password)
    Здесь мы проверяем существующий уже зашифрованный пароль на соответствие с тем, что в бд
    с помощью функции bcrypt.compareSync, который их как раз сравнивает

  Создали отдельный middleware на проверку токена - authMiddleware:

  const token = req.headers.authorization.split('')[1] // Bearer asfasfasfasfasf
  Что значит?
  Токен обычно лежит в headers в authorization, но помимо него там находится и тип токена,
  чаще всего - Bearer, он нам не нужен, берём только токен

  const decoded = jwt.verify(token, process.env.SECRET_KEY)
  req.user = decoded
  Что значит?
  Расшифровываем токен и помещаем в user его токен

  Добавили checkRoleMiddleware для проверки роли пользователя чтобы доступ к post функциям был
  только у админа
